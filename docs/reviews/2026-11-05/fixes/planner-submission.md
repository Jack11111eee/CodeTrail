## 实际任务证据

用户报告的任务 `j_9149d74918a85f0b` 在第 3 次尝试的规划阶段失败，耗时约 1 分 57 秒，错误为 `Repository planning worker exited without submit_plan.`。本次只读检查了该任务及对应调用记录，没有修改历史错误或模型配置。

- 配置为 Anthropic Messages API 兼容网关、`deepseek-v4.1-flash`，单次输出上限 4,096 tokens。
- 两次有完整调用记录的失败均已进行了大量目录浏览与文件读取，基本连接及已有工具调用是成功的。
- 两次失败的最后一条模型响应均恰好消耗 4,096 输出 tokens，分别紧接着任务失败。这强烈指向最终规划响应被输出预算截断，随后没有完成 `submit_plan`。
- 旧记录没有保存原始 `stop_reason`，因此“截断”是基于触顶调用记录的判断，不将其表述为已经读取到原始终止原因。
- 原实现对模型结束响应但尚未提交规划的情况直接抛通用错误，没有定向恢复，也没有提示输出上限。

## 修复

- 规划中间件检查响应：模型尚未提交规划、没有有效工具调用且没有使用过恢复时，追加一次定向提交。
- 复用当前请求中已收集的研究上下文，不把截断的助手尾部加入下一次请求，也不从头启动探索。
- 恢复调用仅暴露 `submit_plan`，使用强制工具调用，要求简短标题、精简用途、保留必要覆盖，省略非必要可选字段和代码正文。
- 保持用户的单次输出上限、模型、地址和 Key。额外模型调用仍走原有计量与配额链路。
- 自动恢复最多触发一次；持续截断或仍不提交时停止，并提示调整输出上限或检查工具调用兼容性。调整配置后需要重新提交分析，旧任务仍使用提交时固定的模型配置。
- 面板通过结构化活动显示“规划响应达到输出上限，正在压缩并重新提交规划（1/1）”或“模型尚未提交规划，正在定向提交（1/1）”。不展示模型内部推理内容。
- 保持原有禁止 Agent 委派的中间件在最终模型边界生效。
